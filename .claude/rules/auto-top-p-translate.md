# Auto Top-p Translate

- **Background service, not a workflow mode.** `translation_service` runs beside any workflow in both modes, never takes a workflow lease or sleep-inhibitor owner, and never blocks or stops a parent. Settings (enabled, paused, batch translation, translated modes, ordered languages, one translator submitter role, one translator validator role) are configured in the Auto Top-p Translate window, never in workflow settings; its Skills And Enhancements row can also enable or disable it, even while a workflow runs. Settings persist as the non-secret `runtime_settings.json` key `auto_translate`; hosted mode accepts OpenRouter roles only. Settings saves never change enabled, paused, or Translate all; only control actions do, and a save without a modes list keeps the saved one. Translations live only in the derived SQLite cache `<data root>/auto_translations/` and never enter workflow/research model context, RAG, canonical artifacts, or WebSocket payloads. A viewer's text/PDF downloads save the language it shows: the complete translation of that exact original with a language-suffixed filename, otherwise the original; `.lean`, certificate, and ranked-group exports stay original.
- **Sequential parts with editing.** A job (one document in one language) translates the next logical part: the translator sees the source document and the translation built so far (windowed around the part only when they cannot fit), chooses the longest natural part it believes it can translate without error, always in document order from the first untranslated paragraph-level unit (bounded only by its output budget and what both roles' prompts can show beside the part, never a fixed size cap), and may edit already-translated units to fix errors. Attempts run in series at temperature 0.0, each seeing the part's earlier attempts in judgment order and their feedback (newest five whole rejected or automatic-check entries, oldest dropped first, never the newest; accepted attempts always shown); a windowed prompt keeps as much of that feedback as fits, and the validator always sees every unit an attempt edits.
- **Part stop rule.** A part finalizes when the validator has accepted three attempts, or at least one is accepted and the translator then answers "keep" twice in a row (naming accepted attempts as already perfect, with no new text). The newest accepted attempt becomes final (for keeps, the one both keeps name). Resubmitting an earlier attempt unchanged counts as keeping it, and keep naming rejected attempts is a dispute the validator re-judges with the translator's notes. The first accepted attempt locks the part's range; follow-up attempts are accepted only if at least as good; accepted edits apply at once and in order, an edit the part's attempts already made is applied only once, and rejected text never enters the translation. No cap: rejections continue with feedback until the rule holds, the user pauses or disables, or a repair state is entered.
- **Pre-checks before the validator.** Deterministic checks (unit coverage and range, placeholders, paragraph markers, delimiters, length ratio, edit anchors that match exactly once, the same unit checks on every edited unit, and edited units the validator's context cannot show beside the part) are recorded as failed-automatic-check attempts whose feedback reaches the next attempt, never as validator decisions; a translator reply that is truncated or still unparseable after one bounded JSON repair is recorded the same way. Optional `translator_notes` explain choices or dispute feedback; the validator weighs them on merit but verifies them.
- **Failures are operational.** Provider, parser, context, and truncation failures never become validator rejections. Retries use the shared seams with workflow mode `translation`; credit exhaustion waits for provider reset; hard provider repair, a unit or part that cannot fit, or two consecutive output truncations from one role (counted per part, reset on entering repair) enter a visible `repair_required` state cleared by a settings change or Retry. Recorded retry, credit-wait, and repair activity carries the failed call's route identity (workflow mode and role only for non-model waits), the wait, and bounded error detail, so the Progress tab shows each wait once with its route. Malformed validator contracts re-validate the same attempt. Translation JSON uses the shared parser with only its newline-prefixed LaTeX pre-escapes disabled, because math is masked. Persisted translation provider notifications keep workflow mode `translation`, are capped at five, and are evicted before any other workflow's notifications.
- **Model calls.** Exact roles `translation_submitter`, `translation_validator`, `translation_language_probe_N`; every call runs inside `background_service_call("translation")` (excluded from workflow token totals and paper/Tier 3 model credits), disables Boost and Supercharge, and never receives Assistant memory.
- **Queue and parallelism.** Jobs rank viewed items first, then current-run and user-requested work, then Translate all work, each by kind (proofs, then papers/final answers/live papers, then brainstorms and other outputs) and the user's language order; jobs yield after every finalized part or provider wait. Viewing priority lasts ten minutes from a viewing registration or lookup, and viewers refresh it while their documents are unfinished. One job runs at a time app-wide unless opt-in Batch translation runs as many as the translator and validator both support (cloud providers up to the per-model concurrency limit; LM Studio up to the loaded copies of the model, counted in the background); when the limit drops, running jobs beyond it (counted beside a running Translate all lane job) yield at their next attempt. While Translate all is on and the connection can run more than one job, it keeps one job of its own (beside the single job, or one of the batch jobs) until that job ends, taking it only when the connection has a free job; other work never preempts current-run jobs, and Translate all work in an ordinary slot yields to waiting viewed or current-run work. A cache clear starts no job until it finishes. Waiting documents show their live queue position, or what translation is waiting for.
- **Segmentation.** Versioned, deterministic, and independent of model settings. Each paragraph is a unit (one over about 600 masked tokens splits at sentence, then word, boundaries); math, inline code, URLs, and LaTeX references are masked as placeholders (renumbered document-wide for model views), and both prompts require numbers and unmasked mathematics to stay exactly as written, never localized; fenced code and Lean blocks, letterless text, hard-coded markers, separators, proof-entry headers and labels, and every structural line the paper/proof parsers read stay verbatim. Identity assembly reproduces the source byte-for-byte, and translated papers must parse to the same proofs. When a document changes, matching units keep their translations, the part in progress survives while its accepted work still maps, and finalized units are reused across documents. Several viewer and discovery keys may share one content hash; auto-targeting and priority come from any key, and status rows echo the requested key. Lean code and app UI text are not translated yet; future UI and Lean-pseudocode translation must reuse this engine through new segmentation profiles.
- **What is translated.** Only the current run of each mode checked under Current runs is discovered automatically (default: Autonomous Research, Aggregator, Single Paper Writer; developer-only LeanOJ defaults off): the active autonomous session's complete papers and completed brainstorms (the legacy roots' when no session is active), plus that session's completed final answer and non-LeanOJ proofs; while each manual mode's saved prompt marks a run, the Aggregator's results and manual-store proofs, and the Single Paper Writer's manual-store proofs and its Live Paper once nothing is writing it; the loaded LeanOJ run's proofs. New outputs (completed papers, final answers, brainstorms, and critiques; verified or registered proofs; accepted Aggregator submissions; LeanOJ verifications), settings saves, and Enable/Resume/Retry trigger a debounced rescan; run starts, stops, fatal stops, clears, and prunes also re-run Translate all's enumeration while it is on. Anything else translates while a viewer shows it in a selected language, after a user requests it (a saved doc-key and language request that translates at current-run priority until done, survives restarts and cache clears, and covers every active language when made while the original is shown), or through Translate all: a persisted control action (cancellable, cleared by disable or a cache clear, finishing by itself) that enumerates every older output the app still lists for the checked modes (paper and final-answer history, pruned papers, proof libraries, inactive manual content, LeanOJ history) with the document identities those viewers register, never content a clear removed, and names outputs it could not list in its finish message.
- **Languages.** The backend catalog lists English, Mandarin Chinese, Hindi, Spanish, Modern Standard Arabic, and French first, then A–Z. A JSON self-report probe (run automatically once per saved model set when the check is missing or stale) marks catalog languages both the translator and validator models list as proficient and offers languages outside the catalog that both list as proficient extras; others render grey with a text warning. Unmatched freeform languages always carry the warning; custom and extra keys are computed by the backend.
- **UI.** Users see it as "Foreign Language Translation w/ Top-p", including in its Live Activity route label ("Auto Top-p Translate" stays the internal name); a Skills And Enhancements row and modal configure it, and the modal's enable section explains and links Top-p Exploration. Under the modal's main controls, the Current runs checklist (its LeanOJ row developer-only in UI and payload; while developer mode is off, an app-level gate re-saves settings without a saved LeanOJ mode) and the Translate all older items button each carry a "?" explanation; library pending notices point to Translate all, and an older backend without modes shows the checklist as unavailable instead of re-checking every mode. Every item of translatable output (each proof card, paper, brainstorm, results view, and the Assistant Memory Bank proof preview) always shows its own Language switch inside the app, even while translation is off: Original plus every selected language, with a language not yet finished for that item greyed out (still selectable; choosing it translates that item first). A choice applies to that item only; items without one follow the Default language set in the modal. Each switch carries a Request translation button whenever a pending document would otherwise stop with the viewer (and always while the original is shown), a pending notice with progress, queue position, or what translation is waiting for, and translated content only when complete. Progress is shown as percentages and older-item counts, never as internal unit counts; activity lines name the document, and the running part shows where it sits as a percentage range. Viewers they register again whenever the service generation changes (a control action, settings save, repair, cleared cache, or backend restart) and retry failed registrations with backoff. Content is rendered through the existing sanitized paths with language-suffixed document identities. The feature is not developer-gated; while translation is disabled only the status read runs, and viewers send no translation requests. While it is on, items shown in the original only read per-language progress through the read-only `POST /documents/progress`, which never registers, views, or requests them.
